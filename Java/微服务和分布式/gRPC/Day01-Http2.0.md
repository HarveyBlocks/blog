# Http2.0

## Http1.x协议

### Http1.0

-   请求响应模式

-   短链接协议/无状态协议

    -   连接响应完成之后就断开连接, 后续服务端就不认识客户端了
    -   解决状态问题使用Http Session, 是在协议之上, 为了补漏洞, 做的技术性设计, 是一种妥协的做法

-   Http基于TCP

    -   但TCP是长链接(三次握手连接, 三次回收断开连接), Http请求结束就强制断开连接

-   传输文本结构

-   单工

    -   无法实现服务端的推送

    -   变相实现推动 , 只能采用客户端轮询

        客户端轮询导致发送大量无意义的请求, 占用大量服务端的资源, 影响服务端的吞吐



### Http1.1



-   请求响应模式
-   有限长链接协议
    -   请求之后将保持连接一段时间
    -   这段时间由HTTP的头`keepalive`决定
-   WebSocket双工
    -   通过升级的方式, 升级到websocket
    -   实现服务端到客户端的推送
    -   websocket是另一种协议, Http1.1还是不能双工QAQ



### 总结

-   使用文本结构, 效率低
-   本质上无法实现双工
-   资源的获取, 需要多次请求, 也就需要多次连接
    -   请求HTML
    -   请求JS
    -   请求CSS
    -   浏览器会去异步去请求JS和CSS, 会同时占用三个连接, 尽管只是一个界面



## Http2.0

-   长链接
-   二进制协议
    -   效率高
    -   可读性差
-   协议设计上就支持双工
-   多路复用
    -   一个请求可以请求多次或多个数据



### 多路复用

-   数据流 stream
    -   一个Steam获取一个资源(CSS/JS/HTML/等)
    -   一次请求-响应携带多个Stream, 完成多个数据的获取
    -   数据流的优先级
        -   优先级高的数据流先获取资源
    -   流控
        -   客户端发送数据太频繁
        -   能暂停发送数据
        -   TCP协议里是滑动窗口来实现
-   消息 message
    -   一个Stream携带一个Message
    -   Stream是Message的载体
    -   Message实质性地具有数据
-   帧 frame
    -   Message携带两个帧
    -   一个携带head
        -   请求方法
        -   http版本
        -   客户端载体(Chorm)
        -   等...
    -   一个携带body
    -   Get请求一个Frame, 因为没有Get没有响应体
