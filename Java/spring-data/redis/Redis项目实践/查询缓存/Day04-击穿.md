# 缓存击穿

>   也称为热点key问题
>
>   一个被**高并发**且**缓存重建业务较复杂**的key突然失效了, 无数的请求访问会在瞬间给数据库带来巨大的冲击

因为请求太多太快, 数据库写到缓存的逻辑耗时太长, 其数据不一致的时间差,造成了大量请求直冲数据库, 

而且, 这些直冲数据库的线程都会让数据库把数据写到缓存里去

就这样直接给把数据库给干碎了

学到这里了我突然有了一个疑问: 连接池是摆设吗? 

## 解决方案

### 互斥锁

数据库数据写入缓存的过程做成一个锁

1.  查询缓存, 未命中

    2.  获取互斥锁成功
    3.  查询数据库重建缓存数据
    4.  写入缓存释放锁

    2.  获取互斥锁失败
    3.  **等着 ** => 性能变差
    4.  再次尝试能否从缓存拿到数据

### 逻辑过期

想想逻辑删除

存在redis里热点key, 设定它永不过期

为热点key**增加字段expire, 代表逻辑过期时间**

1.  用户查询缓存, 发现逻辑时间已经过期

    2.  获取互斥锁成功

        为了解决锁导致的的阻塞问题

        1.  开启新的线程, 查询数据库重建缓存数据	
        2.  写入缓存, 重置逻辑过期时间
        3.  释放锁

    3.  主线程返回过期的数据(也能用, 只是过期了)

    2.  获取互斥锁失败

        说明有线程在更新数据了, 再次撞破头一样去枪锁没有意义

    3.  返回旧数据(也能用, 只是过期了)

### 优缺点比较

-   互斥锁

    -   优点
        -   没有额外的内存消耗
        -   保证了一致性
        -   实现简单
    -   缺点
        -   线程需要等待, 性能收到影响
        -   可能有死锁风险

-   逻辑过期

    -   优点

        -   线程无需等待, 性能较好

    -   缺点

        -   不保证一致性

            又不是完全不能用了, 而且等其他线程更新完了, 又是正确的数据了

        -   又额外的内存消耗

            `expire`字段

        -   实现复杂
