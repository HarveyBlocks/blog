# 缓存更新策略



## 缓存的一致性问题

数据库中的数据被修改, 缓存不知道



## 更新策略

### 内存淘汰

####描述

最初时用来解决Redis内存不足的问题

内存不足时触发这种机制

不用自己维护, 利用Redis的内存淘汰机制, 当内存不足时自动淘汰部分数据, 下次查询时更新缓存

可以自己配置

#### 一致性

一定程度上能达到一致性

可是这个机制不是主动保持一致性. 什么时候淘汰, 淘汰什么数据, 我们都不知道, 也不能主动决定

一致性差

####维护成本

好处是维护成本无

### 超时剔除

#### 描述

利用TTL自动删除数据, 下次查询更新缓存

#### 一致性

时间设置的短, 一致性好, 但数据IO变多效率变低

时间设置长, 一致性差, 但数据请求少

而且一个数据如果一直被访问, 一直保持刷新, 不是没办法更新了吗?还是有点被动

而且数据的一致性依然存在延迟

一般

#### 维护成本

低

### 主动更新

####描述

编写业务逻辑. 在修改数据时即刻更新缓存

#### 一致性

好

#### 维护成本

高

### 策略选择

-   低一致性需求
    -   使用内存淘汰机制
    -   可用超时剔除兜底
    -   例如**店铺类型**的查询缓存
-   高一致性需求
    -   主动更新
    -   以超时剔除作为兜底
    -   例如店铺详情查询

## 主动更新的实现模式

1.  **Cache Aside Pattern**
    -   由**缓存的调用者**,在**更新**数据库的同时更新缓存
    -   有更高的可控性
2.  **Read/Write Through Pattern**
    -   将缓存于数据库**整合为一个服务**, 由服务来维护一致性
    -   调用者调用该服务, 无需关心其一致性
    -   维护服务比较复杂
3.  **Write Behind Cacheing Patthern**
    -   调用者只操作缓存, 无论增删改查全在数据库做
    -   由其他线程的**异步将缓存的数据持久化到数据层**, 保持最终一致性
    -   异步时不时地去看看缓存有没有变化, 一次性将数据写入到持久层, 减少请求, 增加效率 
    -   如果对缓存做了好几次更新, 没必要把每次更新都同步到持久层, 只需要将最终的数据持久化达到数据库就好了
    -   但是异步任务比较复杂
    -   还没触发异步的时间内, 存在数据不一致
    -   由于缓存是内存存储, 一旦在没触发异步的时间内宕机数据就丢失了



-   为了~~钱~~综合考虑, **Cache Aside Pattern**成为了最终选择



## Cache Aside Pattern实现

### 分析问题

1.  删除缓存还是更新缓存

    -   更新缓存

        -   每次更新数据库都更新缓存
        -   如果**一直改而没人查**
        -   无效写操作较多

    -   删除缓存

        -   更新数据库时让缓存失效, 查询时再更新缓存

    -   也就是说, 想要更新数据

        -   删除缓存

        -   在数据库中更改

        -   查询的时候,由前面的代码, 会自动从数据库把数据拿到缓存

2.  保证更新的原子性

    -   保证缓存和数据库操作的同时成功和失败
    -   利用事务的一致性
    -   分布式系统, 利用TTC等分布式事务方案

3.  保证线程安全

    -   先操作缓存还是先操作数据库? 

    -   先删除缓存再在数据库中更新

        -   存在问题:

            1.  在删除缓存之后, 数据更新之前

            2.  **突然!** 有人来查数据, 缓存查不到, 去数据库拿

            3.  **这时候拿到的数据库里的数据是旧的, 没更新的**

            4.  拿到的**旧数据**存入缓存

                ==数据不一致产生==

            5.  数据库中的数据更新完毕, 但缓存不知道

            **从此缓存的数据就是旧的, 谁查都是旧的**

        -   问题产生的原因: 

            ​	缓存删除的很快,缓存写(旧数据)很快

            ​	**数据库更改(更新操作很复杂)的很慢**

            ​	给足了机会造成乘虚而入

    -   先在数据库中更新, 再删除缓存

        -   存在问题:

            1.  有人来向缓存查数据, 缓存内没有数据, 就**去数据库拿数据**, 且已经拿到了数据

                **但是还没有写入到缓存**

            2.  另一个人更新了数据库, 把数据改成了新数据

            3.  又把缓存里的数据删除了(由于此时缓存里还没有数据, 所以删了个寂寞)

            4.  那个来查数据的人, 把**没更新的旧数据**写入了缓存

                ==数据产生不一致==

            5.  数据库更新完毕, 缓存内也存在, 但是引起了数据不一致

        -   问题产生的原因:

            ​	需要缓存内在一开始没有数据

            ​	缓存写入操作存在间隙,**可是这个间隙很小**

            ​	数据库更新, 删除缓存乘虚而入, **可是数据库更新比较复杂, 花的时间比较长**
        
            ​	所以==很难乘虚而入==
            
        -   加个分布式锁, 全局只有一个线程可以写缓存, 写缓存之前先查, 查看是否有缓存, 有了缓存就检查版本号, 持有更新版本的数据可以写入缓存. 但是这样效率低了, 缓存高效的特点失效了

***综上 :***

由**缓存的调用者**,在**更新**数据库的同时更新缓存

利用事务的一致性(本实践是单体的项目)

先在数据库中更改

再删除缓存
