# 共同点

-   都用来完成一次会话内多次请求间数据共享


# 不同点

## 存储位置

-   Cookie存储在客户端
-   Session存储在服务端

## 安全性

-   Cookie在互联网中到处传,不安全
-   Session在服务端本地,安全

## 数据大小

-   Cookie最大3KB
-   Session无大小限制

## 存储时间

-   Cookie长期存储(有长期存储的可能)
-   Session默认30分钟(只能设置时间,不能无限)

## 服务器性能

-   Cookie不占用服务器资源
-   Session占用服务器资源



# 用处

## Cookie

-   购物车
    -   存储时间需要长，重启之后仍需要数据保存
-   偏好设置(网页背景色,字体等)
    -   存储时间需要长，重启之后仍需要数据保存
-   记住账号密码
    -   存储时间需要长，重启之后仍需要数据保存
    -   至于安全性?客户自己选择的，自己负责，管我啥事?





## Sesion

-   用户信息
    -   敏感信息，需要安全
-   验证码
    -   你不能让客户端通过Cookie获得验证码呀!那张图片是客户端获取验证码唯一的途径!









## 表单输入错误是否清空Q&A

Q:  有些网站账号密码输错了,表单内容依据存在,有些网站却会把表单清空,这两种要分别怎么设计网页

GPT:

1.  保留表单内容：如果你希望用户在输错账号密码后保留原有的表单内容，可以在用户提交表单时将表单数据存储在**会话（session）**或者数据库中。当用户输错密码时，可以在页面重新加载时从会话或数据库中获取之前填写的表单数据并自动填充到相应的输入字段中。
2.  清空表单内容：如果你希望用户输错密码后清空表单内容，可以在处理登录请求时，根据用户名和密码的验证结果，判断是否清空表单。如果用户输错密码，可以在返回的页面中不加载之前的表单数据，或者在前端脚本中清空表单字段的值。
