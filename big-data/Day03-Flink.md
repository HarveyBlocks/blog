# Apache Flink

> 流处理引擎

Flink 本质是一个为**无界数据流**设计的分布式处理引擎。它通过一系列底层机制，让开发者能够在持续不断的数据流上构建可靠、高性能、可容错的计算应用。

## 流

无界(Unbound)流(Stream)

- 任务一直产生, 用不停留

  比如消息队列不断产生消息

- 依赖时间或watermark来进行阶段性的计算

- 需要开启checkpoint, 用于数据恢复

- 需要长期存储中间State

- 数据不断, 输出不断

有界(Bound)流- **批**(Batch)

- 任务运行完就结束
- 不需要checkpoint, 任务复现容易
- 不需要watermark, 一次性处理完
- State在运行完任务之后释放
- 全部处理完之后输出(也可以在中途输出几次)



## 处理机制

### 无界数据流与事件时间处理

#### 机制解释
- **无界数据流**：数据持续产生，永无止境（如用户点击、传感器读数）。处理无界流的核心挑战是：数据无限、可能乱序、且无法预知全部。
- **事件时间**：事件实际发生的时间戳（由业务系统生成），而非数据到达 Flink 的处理时间。使用事件时间才能正确反映业务时序。
- **Watermark（水位线）**：一种衡量事件时间进度的机制。它表示“事件时间早于 Watermark 的数据已经基本到齐”，用于触发基于事件时间的窗口计算。Watermark 通常定义为 `当前观察到的事件时间最大值 - 预期最大乱序延迟`。

#### 设计思路
在设计流处理作业时，如果需要按事件真实发生的时间进行统计（如每5分钟的用户行为聚合），必须启用事件时间语义，并配置合理的 Watermark 生成策略。Watermark 允许系统容忍一定程度的乱序：只要迟到数据不超过设定的延迟，就能被正确归入所属窗口。

#### 业务示例
**电商实时热门商品统计**  

需要统计每分钟内点击量最高的商品。用户点击日志可能由于网络延迟、移动端离线等原因乱序到达。  

- 使用事件时间（用户点击时间）作为时间基准。  
- 设置 Watermark 生成策略：允许乱序延迟 10 秒。  
- 每收到一条日志，更新当前最大事件时间；周期性生成 Watermark = 最大事件时间 - 10秒。  
- 当 Watermark 超过窗口结束时间（如 10:01:00），触发计算该窗口（10:00:00-10:01:00）的点击量。这样，晚到 10 秒内的点击仍会被正确计入。 

**效果**：热门榜单更准确，能抵御网络抖动带来的数据乱序。



### 状态管理与容错

#### 机制解释
- **状态（State）**：流处理中需要“记住”的中间数据，如聚合值、去重集合、模式匹配的上下文。Flink 提供键控状态（Keyed State）和算子状态（Operator State）。
- **键控状态类型**：
  - `ValueState<T>`：每个键保存一个单值。
  - `ListState<T>`：每个键保存一个列表。
  - `MapState<UK, UV>`：每个键保存一个映射。
  - `ReducingState` / `AggregatingState`：自动聚合的状态。
- **状态后端（State Backend）**：状态的存储引擎。主要有三种：
  - **MemoryStateBackend**：状态存储在 TaskManager 的堆内存中，适合小状态、快速开发。
  - **FsStateBackend**：状态存储在 TaskManager 内存，Checkpoint 时持久化到文件系统。
  - **RocksDBStateBackend**：状态存储在本地 RocksDB（LSM 树引擎）中，支持超大规模状态（TB 级），通过异步 Checkpoint 持久化。
- **Checkpoint（检查点）**：分布式快照机制，定期保存所有算子的状态和消费位置，用于故障恢复。基于 Barrier 对齐实现一致性快照。
- **状态 TTL**：可配置状态的生存时间，自动清理过期数据，防止状态无限增长。

#### 设计思路
当计算需要跨多条记录维护信息时，必须使用状态。设计时需评估状态大小、访问模式，选择合适的后端和 TTL 策略。通过 Checkpoint 保证容错，恢复时从最近成功的 Checkpoint 重置状态，实现精确一次语义。

#### 业务示例
**实时反欺诈：高频交易检测**  

检测一个账户在 1 分钟内交易次数超过 5 次则触发告警。  

- 使用 `keyBy(accountId)` 得到键控流。  
- 在 `ProcessFunction` 中定义 `ListState<Long>` 保存最近 1 分钟内每笔交易的时间戳。  
- 每来一笔交易，将当前时间戳加入 ListState，并调用 `ListState.get()` 遍历，剔除超过 1 分钟的时间戳，然后判断剩余数量是否 >5。  
- 设置状态 TTL 为 1 分钟，自动清理过期条目。  
- 启用 Checkpoint（如每 10 秒），将状态持久化到 HDFS。若任务故障，重启后自动恢复状态，继续从故障点消费数据，不会重复告警或漏告。 
**效果**：内存可控（旧数据自动过期），故障后状态一致，业务逻辑正确。



### 精确一次语义（Exactly-Once）

#### 机制解释
每条数据对最终结果的影响恰好一次，不丢不重。分布式系统中极难实现，需协调内部状态和外部输出。

- **内部状态**：通过 Checkpoint 保证状态的一致性，故障恢复后状态回滚到快照点。
- **Source 可重置**：数据源需支持重新消费（如 Kafka 可重置 offset）。
- **Sink 的幂等性或事务性**：
  - **幂等写入**：多次写入相同结果不会产生副作用（如 Redis 的 set 操作）。配合 at-least-once 源可实现 exactly-once 效果。
  - **事务写入**：利用两阶段提交协议（2PC）保证写入的原子性。Flink 提供 `TwoPhaseCommitSinkFunction`，在 Checkpoint 时预提交，Checkpoint 成功后真正提交；若失败则回滚。

#### 设计思路
在涉及金融计费、库存扣减等要求数据绝对准确的场景，必须启用 exactly-once。需要确保 Source、Flink 作业、Sink 三端协同：
- Source 支持 offset 重置。
- Flink 启用 Checkpoint，并设置 Exactly-Once 模式（默认）。
- Sink 需支持事务（如 Kafka、Pulsar）或幂等性（如 HBase、Redis 的 upsert）。

#### 业务示例
**广告点击计费系统**
按每次点击向广告主收费，必须保证计数精确一次。  

- Source：从 Kafka 消费点击事件，Kafka 支持 offset 重置。  
- Flink 作业：使用 `keyBy(adId)` 聚合点击次数，状态存储当前计数。  
- Sink：结果输出到支持事务的 Kafka Topic（用于后续计费服务消费）。  
- 开启 Checkpoint（如每 5 秒），使用 `ExactlyOnce` 模式，并实现 `TwoPhaseCommitSinkFunction`。  
- 当 Checkpoint 完成时，Sink 提交事务，使计费数据对外可见。若作业失败，重启后从 Checkpoint 恢复状态和 offset，重新处理故障期间数据，但事务未提交的数据会被丢弃，保证最终计费不重不漏。



### 流批一体

#### 机制解释
- **概念**：Flink 用同一套 API（DataStream API / Table API）处理无界流和有界批数据。批处理被视为有界流的一种特例。
- **底层统一**：批作业和流作业在运行时都转化为 `DataStream` 图，只是执行策略不同（批处理可做更多优化，如调度策略、内存管理）。同一套业务逻辑可以在实时流和离线数据集上无缝运行。

#### 设计思路
当业务既需要实时处理，又需要定期跑批（如历史数据重跑、夜间补数据）时，设计一套通用逻辑，仅切换数据源即可。这避免了维护两套代码，减少开发成本，保证逻辑一致性。

#### 业务示例
**用户行为 ETL 与模型修正**  

白天实时消费 Kafka 中的用户点击流，清洗后写入实时报表。每晚需要对全量历史日志（HDFS 上的 Parquet 文件）重新计算，以修正因实时处理可能产生的误差。  

- 编写 Flink SQL 作业：定义 Source 为 Kafka 实时表，Sink 为报表表。  
- 批处理时，将 Source 替换为 HDFS 上的历史文件表（同样 schema），其余逻辑完全相同。  
- Flink 自动识别数据源为有界，采用批执行模式，高效处理海量历史数据。 
**效果**：实时与离线逻辑 100% 一致，维护成本减半。



### 窗口操作（Windowing）

#### 机制解释
- **窗口**：将无限数据流切分成有限块进行分析。Flink 提供丰富的窗口类型：
  - **滚动窗口（Tumbling）**：固定长度，无重叠，如每 5 分钟一个窗口。
  - **滑动窗口（Sliding）**：固定长度，有重叠，如每 1 分钟计算过去 5 分钟的数据。
  - **会话窗口（Session）**：基于活动间隙划分，如用户连续操作，超过 30 秒无新事件则结束会话。
- **触发器（Trigger）**：决定窗口何时计算输出，可自定义（如提前输出部分结果、迟到数据处理）。
- **驱逐器（Evictor）**：在窗口计算前移除某些元素（较少用）。

#### 设计思路
选择窗口类型取决于业务聚合的粒度。结合事件时间和 Watermark，可处理乱序数据。对于特殊需求（如需要实时预览窗口中间结果），可自定义触发器提前输出。

#### 业务示例
**实时监控 API 接口 QPS** 
监控每秒钟请求数，超过阈值则告警。  

- 使用滚动窗口，窗口大小 1 秒。  
- 事件时间可能不关键，可用处理时间（ProcessingTime）窗口。  
- 每来一条请求，计数加 1；每秒窗口触发一次，输出该秒内总请求数。  
- 若请求数 > 1000，触发告警。 
**效果**：秒级实时监控，及时发现流量高峰。



### 丰富的连接器与外部系统集成

#### 机制解释
- **连接器（Connector）**：Flink 提供预定义的 Source 和 Sink 实现，与各类存储系统无缝对接，如 Kafka、Kinesis、文件系统（HDFS、S3）、数据库（JDBC、Elasticsearch、HBase）、消息队列（Pulsar、RabbitMQ）等。
- **Source 特性**：支持分区发现、偏移量提交、水印生成。
- **Sink 特性**：支持至少一次、精确一次语义（通过事务或幂等性）。
- **Side Output**：可将不符合预期的数据分流到旁路输出，便于异常处理。

#### 设计思路
在设计数据管道时，先确定数据的来源和去向，选用对应的连接器。利用 Side Output 分离脏数据或特殊事件，写入死信队列（如 Kafka 的 DLQ）。连接器封装了分布式一致性和并行度细节，让开发者聚焦业务逻辑。

#### 业务示例
**实时日志清洗平台**
从 Kafka 消费原始日志，清洗过滤后分别存储到不同系统。  

- Source：Kafka 连接器，配置消费者参数。  
- 使用 Flink SQL 或 DataStream API 进行字段提取、格式转换、数据校验。  
- 主输出：清洗后的数据写入 Elasticsearch，供实时搜索和监控。  
- Side Output：字段缺失或格式错误的日志输出到 Kafka 的“脏数据” Topic，后续人工分析。  
- 关键指标（如每分钟请求量）异步写入 Redis，供大屏展示。  
**效果**：一站式实时数据清洗与分发，所有数据集成通过连接器完成，系统扩展性强。



### 异步 I/O（Async I/O）

#### 机制解释
- **问题**：流处理中常需访问外部系统（如数据库、REST API）来丰富数据（Enrichment）。同步 I/O 会阻塞算子，降低吞吐量。
- **异步 I/O**：Flink 提供 `AsyncFunction` 接口，允许并发发送请求，并在请求返回后异步地处理结果。算子不会等待单个请求，而是继续处理其他元素，当请求完成时回调输出结果。
- **设计要点**：
  - 配置并发请求数（`capacity`）控制背压。
  - 设置超时时间，处理失败请求（重试、降级或丢弃）。
  - 注意顺序性：若需保持元素顺序，可启用 `ordered` 模式；若可容忍乱序，则用 `unordered` 提升吞吐。

#### 设计思路
当每条流数据需要查询外部系统（如用户画像数据库）来补充信息时，使用异步 I/O 代替同步调用，大幅提升吞吐量。需根据外部系统特点调整并发度，并做好异常处理。

#### 业务示例
**实时用户点击日志增强** 
解析点击日志中的 userId，需要从 HBase 中查询用户画像（年龄、性别、会员等级）来丰富数据，供后续分析。  

- 实现 `AsyncFunction`，在 `asyncInvoke` 方法中异步发起 HBase 查询（使用 HBase 的异步客户端或线程池 + Future）。  
- 设置并发请求数为 100，超时 5 秒。  
- 请求成功时，将画像字段合并到日志中并输出；失败时可输出到 Side Output 或填充默认值。  
- 由于下游分析不关心顺序，使用 `unordered` 模式提高吞吐。  
**效果**：相比同步查询，吞吐量提升数倍，且不会因外部系统延迟阻塞整个流。
