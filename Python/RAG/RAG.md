# RAG

## 概念

> Retriever Augmented Generation

在提示词进入LLM之前, 对其进行**增强( Augmented )**

1. 先进行检索, 收集相关信息 
2. 然后为语言模型生成(**Generate**)一个增强提示词, 增强提示词包括:
   - 原始问题
   - 检索到的信息

检索(retrieved)到的信息, 是由RAG系统中的组件 **Retriever** (检索器)

Retriever 存储可信, 相关, 且可能私有的信息

当 RAG 系统接收到提示词时, Retriever 会检索 **知识库** 中最相关的信息

## 应用

> 构建一个自己的代码库为知识库的 RAG 系统

- 从代码仓库中检索相关的类, 定义, 文件
- 生成代码
- 回答项目的有关问题

> 企业定制专属聊天机器人

- 构建公司自己的产品, 政策, 沟通准则. 把这些企业文档作为数据库部署LLM
- 搭建客服聊天机器人, 了解产品信息, 库存情况, 或常见故障排除步骤
- 提供相关文档

## 架构

  一般的LLM系统

1. 客户输入提示词 Prompt
2. LLM生成文本内容, 并返回响应

RAG 系统

1. 客户端输入提示词 Prompt
2. Retriever 在 **Knowledge Base** (知识库) 中进行检索到提示词最相关文档
3. 系统把相关稳定男那个信息加入到 **Original Prompt** (原始提示词)中, 创建 **Augmented Prompt**
4. 将  **Augmented Prompt** 发送给LLM, LLN生成文本响应客户端



![image-20260303232512021](https://raw.githubusercontent.com/HarveyBlocks/blog_assets/refs/heads/main/Python/RAG/RAG/image-20260303232512021.png)



好处

- 获取原本无法获取的信息(例如内部数据, 个人信息)
- 降低幻觉, 减少泛泛而谈或误导性回复
- 跟上快速变化的信息. 用新数据重新训练模型成本很高, 但是引入 RAG , 改变信息只需要改变 Knowledge Base 内的索引





## LLM

- randomness 一个语境下, 下一个可生成的词有多种可能, 依据词生成的可能性来随机生成
- autoregressive nature 自回归特性, 会查看自己之前生成的词, 并以此进行进一步的生成. 
- 由于 randomness , 生成出不同的词, 而不同的词有自己的生成路径(即词后更可能是哪个词), LLM 对同一个问题可能产生不同的结果

**Hallucination** (幻觉): 在某方面专业的, 特定的信息(例如个人信息和内部数据), 给 LLM 训练的数据很少, LLM 容易生成看起来对, 其实是错误的文本.

上下文限制: 增前了提示词, 导致提示词太长, 一方面, 增加了计算资源的消耗, 另一方面, 超出了上下文窗口的限制

 

## Retriever

- 搭建文档知识库
- 建立索引
- 检索相关文档, 过滤不相关的文档
- 对检索结果的相关程度进行排序

# 检索

## 目标

- 允许用户使用自然语言描述需求
- 知识库大多是备忘录, 知识文档等, 不适合检索, 是松散的信息
- 能够快速检索得出结果

## 架构

1. 系统收到用户的自然语言指令
2. 将指令传给 Retriever(检索器)
3. 检索器访问知识库
4. Retriever 快速判断, 筛选出最匹配内容的文档
5. 将文档+用户的自然语言描述传给LLM

传统 keyword 查找关键词搜索, 精准匹配

Semantic Search 语义搜索技术, 通过理解文档来进行匹配, 更灵活准确

Hybrid Search 混合搜索, keyword 和 Semantic 两种方式的搜索结果, 进行 Merge 后, 再次选出得分最高的结果



## 元数据过滤技术

Retriever 能通过 **元数据** 来缩小查找的范围

- 标题
- 发表日期
- 作者
- 所属版面

使用元数据进行预先过滤的时候, 不是依据提示词进行的, 而是依靠**用户本身的属性**

比如新闻的元数据, 会记录新闻的国家信息, 然后依据用户是哪个国家的, 推送不同新闻, 禁止用户查询其他国家的新闻

## BM25 算法

> Best Match 25 最佳匹配算法, 是一种 keyword 匹配算法
>
> 25 是研发团队第25个提出的评分函数变体

TF-IDF 关键词搜索算法, 见Elasticsearch

BM 25
$$
IDF \times \frac
	{TF \times (k_1 + 1)}
	{  
		TF + k_1 \times (1-b + b \times \frac
		{document\;length}{avg(documents\;length)}
	}
$$
计算相关度分数, 某个关键词在某个文档中的单个的分数, 系统会计算所有关键词的总分, 从而对文档进行排序

- **frequency saturation 词频饱和** 关键词权重会不断降低, 直到其重新出现
  - 保证了出现关键词词频高的文档的分数更高
  - 文档A的关键词词频是文档B的两倍, 文档A的分数不一定是文档B的两倍, 需要降低
- **Document Length Normalization 文档长度归一化** 降低长文档的权重, BM25采用**递减权重**机制
  - 长文档的重要性不会过度降低, BM25会根据文档长度逐步降低调整幅度
- 引入可调超参数
  - $k_1$
  - $b$

## 混合搜索

- 元数据过滤技术
- 关键字搜索
- 语义搜索



检索器

1. 同时对知识库中的数据进行关键字搜索和语义搜索并排序
2. 对搜索出来的两个结果分别通过元数据过滤
3. 对两个结果进行合并 (两个搜索方式的分数评判标准不一样, 排序如何决定?)

逆序秩融合 ( Reciprocal rank fusion )

- 奖励在任一列表中排名靠前的文档
- 允许控制两种搜索方式(keyword/Semantic)的权重
- 忽略两个序列的分数, 排序名次只和原排序的排序名次有关

$$
\frac{\beta_1}{k+N_1}+\frac{\beta_2}{k+N_2}+\frac{\beta_3}{k+N_3}+...
$$



- $N_i$ Rank in list i
- $k$ 超参数, 避免较前名次的搜索结果的数值过大, 例如
  - $k = 0$ , $rank = 1 \to score = 1; rank = 10\to score = 0.1$, 有十倍差距
  - $k = 50$ , $rank = 1 \to score = \frac{1}{50}; rank = 10\to score = \frac{1}{60}$, 只有1.2倍的差距
- $\beta_i$ 超参数, 保证 $\sum_{i=1}^{n}{\beta_i}= 1$ , 用于表示不同排行占据的影响的权重

## 评估搜索质量

需要

- 提示词
- 检索器排序结果
- 标准答案

评估标准

- 精准率 

  - 检索到的相关文档数在检索到的文档总数的比
  - 反映了检索器返回无关文档的情况, 衡量结果的可信度

- 召回率

  - 检索到的相关文档数在知识库中的**相关文档**的总数
  - 表示有多少相关文档被遗漏, 衡量检索器的覆盖程度

- 目标是把相关文档排在前面, 并只返回了这些文档, 否则通常要在这两个标准之间做权衡

  可以使用牺牲一点精准率换召回率, 比如找到更多的文档, 尽管有更多的搜索出来的文档是不需要的, 但是知识库里更多的相关文档被搜索出来了

- top k

  - 用检索器排名最高的前K个文档做评判
  - **平均精准度** ( **Mean Average Precision** ): k 取不同值时, top k 代表不同的文档, 精准值也不同. 使用 k 不同取值下的精准度的平均值, 作为 **平均精准度**. 如果出现无关文档, 会拉低此文档之后所有的精准值, 同时拉低平均精准度.

- 倒数排名(**Reciprocal Rank**), $\frac{1}{rank}$ : 

  - 第一个相关文档在 $Rank \; i$, Reciprocal Rank 的值就是 $\frac{1}{i}$
  - 多次查询的Reciprocal Rank 取平均值, 是为**平均倒数排名**(**Mean Reciprocal Rank**)
  - 反映了平均多靠前的位置, 能在检索器排名中找到相关内容
  - 强调包含至少一个相关文档, 并尽可能排在前面的重要性

## 邻近查找算法

> Nearest Neighbors

### KNN K 近邻算法

1. 为每篇文档创建一个 Embedding vector
2. 把 Embedding vector 插入数据库
3. 将 Prompt 创建一个 Embedding Vector
4. 计算 **Prompt 的向量**和**每个文档的向量**之间的距离
5. 依据距离对文档排序
6. 返回前 K 个文档



### ANN 近似最邻近算法

> Approximate

利用构建数据结构来实现较快的查找

无法保证在数据库中找到绝对最邻近的文档

Navigable Small World 可导航小世界算法

 **近邻图** 数据结构

- 插入一个文档的Embedding vector
  1. 计算待插入的文档向量与其他文档的向量之间的距离
  2. 在这个近邻图内部, 为待插入的文档添加一个节点
  3. 为这个插入的文档, 与离它最邻近的其他文档创建一条边
- 查找 Prompt Embedding vector (**查询向量**) 的近邻节点
  1. 随机选择一个 **候选向量** 的入口点作为起点
  2. 查看当前**候选向量**的每个邻近点, 并计算其中哪个离**查询向量**最近
  3. 重复步骤2, 直到**候选向量**的所有邻近点离**查询向量**都没有**候选向量**本身的距离近
  4. 从此节点开始, 向周围遍历图, 查找距离 **查询向量** 最近的 top k 个节点

优化: Hierarchical navigable small world 分层可导航小世界算法 (HNSW)

依赖于**分层近邻图**, 思想类似于跳表,  随机产生上层节点

## 分块

从知识库中拆成较小的文本块

- 许多 Embadding models 对输入 token 长度有限制
- 提高检索工具的搜索相关性指标
- 确保仅将最相关的文本从文档那个中发送给大预言模型

分块大小的选择. 过大, 则分块不充分; 过小, 失去所有上下文, 再次降低了相关性

### 固定大小分块 

限制每个分块的大小是固定长度, 同时还会截取一部分前文. 

例如限制为250个word, 第二段会有25个word来自第一段的末尾, 然后是之后的225个word. 

**重叠分块**避免了段落脱离上下文被截断的情况. 

重叠部分更长, 一般是对效果是有利的, 但是会冗余信息会增加存储负担.



### 递归字符文本分块

选择一个特定的字符来进行分割, 例如换行符/句点.

考虑文档结构, 提高了相关性语句被放在了同一个分块里的可能性

分块的大小可变, 存在块极大/极小的可能性

同样的思想拓展一下, 源代码文件(例如python), 可以以函数来分块

### 语义分块

> Semantic 

1. 逐句遍历文档一次处理一个句子
2. 逐句判断是否与前几个句子足够相似
   - 当前句子和前面的句子都会被向量化
3. 如果向量足够接近, 差距小于某个阈值, 则认为含义相近, 添加到同一块中
4. 不断持续该过程, 直到差距高于阈值, 切断阈值, 这个句子作为下一段的起点

需要反复计算每个句子的Embadding向量, 成本比较高



> 第一次构建整个知识库时, 可以使用前面的传统分块方法
>
> 异步地, 对每一个文档进行高级的分块策略, 例如语义分块. 
>
> 分完之后再对每个分块进行Embadding向量的构建
>
> 将新分块的向量替换掉知识库里的旧分块的向量
>
> 这样, 对用户无感知, 然后又能构建高质量的知识库. 缺点是一开始的质量不高, 但这是暂时的.

甚至可以使用LLM对文本进行分块, 随着LLM的成本下降, 这也将变得可能

## 查询解析技术

对Promt进行增强, 增强后再进行检索

坏处是增加了一些耗时过程, 当效果不尽人意

### 查询词重写

用户直接输入的 Promt 可能比较糟糕. 可以先一步进行处理, 优化, 甚至重写

使用 LLM 重写查询 Promt 在交给 Retriever 之前

- 去除冗余信息和无关信息
- 澄清歧义
- 增加一些相关术语



### 命名实体识别

> Named Entity Recognition

识别查询中信息类别的技术, 比如地点, 人物, 日期....

这些信息可用于指导检索器的向量检索或元数据过滤 

### 假设文档嵌入

> Hypothetical Document Embeddings

这种方法通过生成一个**假设文档**优化搜索查询. 

例如询问Java的信息, 在检索之前, 先生成一个Java的说明文档, 嵌入提示词, 然后再经过向量化去知识库进行检索

有助于提示检索器, 不仅仅是 Promt 内的文本内容或问题需要注意, 还需要携带一些与问题相关的信息

## 架构

### Bi-encoder

双向编码器, 基础架构

文档和 Prompt 分别被 Embedding Model 嵌入

### Cross-encoder

> 交叉编码器

将文档与Prompt拼接后放入Cross-encoder, Cross-encoder生成一个score, 表示文档和Prompt的匹配程度, 然后取出排名较高的文档

![image-20260311013706207](https://raw.githubusercontent.com/HarveyBlocks/blog_assets/refs/heads/main/Python/RAG/RAG/image-20260311013706207.png)

相较于Bi-encoder, 降低了效率, 但是效果比Bi-encoder好很多

问题在于扩展性极差, 每一个查询都需要吧所有的文档都进行一遍评分

### ColBERT

> Contextualized Late Interaction Over BERT

基于 BERT 的上下文延迟交互

1. 为Prompt 和 Document的**每一个 token** 进行向量化
2. Prompt 中的 $M$ 个 token 都尝试从文档 $N$ 个 token 中寻找与其最相似的 token. 有 $M$ 个
3. 将这些最相近 token 的 $M$ 个相似度score 进行求和后, 得出 $MaxSim$ score
4. 对所有的文档重复此过程
5. 比较出 $MaxSim$ 最大的文档, 表示合适的文档

需要存储的向量数量大量增加

我认为这已经可以看作退化成比较高级的Keyword搜索了, 是否有明显的增加难以论说

## Reranking

> 重排序

通过更强大的Model对检索到的文档进行重排序. 

这个过程中参与的文档较少, 因此可以使用成本更高更强大的Model(例如 Cross-encoder 架构)

Reranking 也可以在重排序之后进一步减少无关文档的数量, 提高质量

或者直接使用 LLM 进行重排序(如果成本允许)



构建索引

1. 文档依据固定长度分块
2. 分块经过Embadding Model, 构建向量
3. 多个向量建立索引
4. 开启异步任务, 逐步地将文档从固定长度分块构造的向量替换成按照语义分块的向量

发送携带 Prompt 的请求

1. 对 Prompt 进行重写
   - 去除冗余
   - 去除无关
   - 澄清歧义
   - 增加专业属于
2. 从Prompt中提取Named Entity Recognition, 存储起来, 用于之后的Meta Data Filter
3. 依据 Prompt 进行假设文档生成, 然后嵌入文档中
4. 将此 Prompt 生成向量 $V_p$
5. 在数据库中寻找距离 $V_p$ 最近的向量, 然后经过Metadata filter, 最终获取 top $k_1$
6. 在数据库中按照 keyword 寻找与 Prompt 重叠最多的, 然后经过Metadata filter, 最终获取 top $k_2$
7. 两个 Rank 合并, 取出对应的 top $k_3$ 分块
8. 将每个分块与Prompt合并, 然后得出相似度 score (Cross-Encoder), 然后取出score 最高的 top $k_4$ 个分块
9. 最终 top $k_4$ 和 Prompt 合并, 发送给最终的 LLM

其中 top k 应当不断缩小, 不断过滤



# Q&A

## Q1

> Origin promt + Augmented prompt 会很长, LLM 怎么记得住?

- 大量预训练数据, LLM 能够整理长文本脉络

- 注意力机制, 在从前往后的 RNN 循环生成中, 能回顾输入前文, 并且抓住**注意力分数高** (相关性)的前文

- 以 Origin promt 为基准, 再次去所有输入信息中提取信息, 相关度低的信息权重会非常低

- RAG 系统不仅检索出相关信息, 并对资料做有关排序, 相关性的资料在前. 帮助 LLM 快速抓住重点

- RAG 会对信息进行整理和重排, 使其条理清晰

  ```markdown
  请根据以下文档内容，回答用户的问题。
  
  文档内容：
  [1] (关于A方面的信息...)
  [2] (关于B方面的信息...)
  [3] (关于C方面的信息...)
  
  用户问题：[用户的原始提示词]
  
  回答：
  
  ```
