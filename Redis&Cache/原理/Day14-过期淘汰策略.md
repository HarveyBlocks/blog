# 过期/淘汰策略

## 判断过期

每当给key设置一个过期时间，该过期时间将会被存储到**过期字典**

过期字典中存储一个`long long`类型的时间对象

该字典实际上是一个hash表，允许在O(1)的时间内查找到过期时间，当查询一个key的时候就会将这个过期时间和现在时间相比较，如果小于现在的时间，redis就会判断这个key已经过期

## 过期策略

redis通常使用 惰性过期+定期删除 作为删除策略使用

### 定时删除

(Redis 准备了这种策略)

在设置key的时候为这个key维护一个时钟，时间到了触发定时任务删除key

内存友好，cpu不友好，过多的定时任务会占用大量的cpu

### 惰性过期

当且仅当用户访问该key，且key过期时才会删除key

**cpu友好，内存不友好**

可能会导致**内存占用过高**，触发内存淘汰

在惰性过期规则中，Redis 在访问或者修改 key 之前，都会调用 `expireIfNeeded` 函数对其进行检查

 `lazyfree_lazy_expire` 参数配置 **同步删除还是异步删除（Redis4.0后）。**默认为同步删除

在异步删除时, 为了防止**并发问题**, 是同步删除过期字典里的key, 然后异步对资源进行释放

### 定期删除

定时随机检查**20个（redis写死的）**设置了时间的key，并删除其中已过期的key

被删除的key超过5个（25%）时，判定redis过期key过多，会重复执行一次该操作，来减少过期key占用过多内存空间的可能

通过**配置定时检查间隔**，和扫描限定耗时来使cpu资源达到最优的平衡效果

为了保证redis不会因为循环过度线程卡死，redis设置了定时删除循环流程的上限，最多不超过25ms一次



## 内存淘汰

就算两种过期策略结合使用，也无法避免出现过期Key的数量很多，导致内存占用过多的问题

因此redis引入了 **内存淘汰** 策略，在内存资源紧张的时候主动删除键值对释放内存空间

### 触发条件

Redis 可以通过参数 `maxmemory` 设置内存最大限制，只有redis内存占用到了这个最大的内存占用时才会触发内存淘汰

64位操作系统该值默认是0代表无上限

32位操作系统该值默认是3GB，因为最多就4GB内存，需要留1GB给操作系统运行



### 配置策略

查看当前的内存淘汰策略

```bash
config get maxmemory-policy
```

通过redis命令配置, 重启就失效

```bash
config set maxmemory-policy <策略>
```

修改配置文件, 重启才生效

```config
maxmemory-policy <策略> 
```

默认策略为 `noeviction`

### 淘汰策略

#### noeviction

> 不淘汰策略

内存不足直接返回错误，**确保数据完整性**，但是会导致写入操作失败，读操作不受影响。

适用于数据绝对不能丢失的场景，例如金融系统中的关键数据

内存不足时通过定时任务持久化数据到数据库主动删除过期key来处理。

#### volatile-lru

> Least Recently Used 局部最少最久未被访问

从**设置过期时间的键**中选择最少使用的键进行删除，优先删除最久未被访问的键

适用于**具备时间局部性的场景**, 例如用户访问了一个资源，那么它很可能在不久的将来再访问一次

传统LRU算法需要维护一个双向链表，一个节点被访问就会被移到链表头，这样链表尾部的就是最长时间未被访问的数据

但是传统的 LRU 算法需要维护一个 map（可以直接通过 key 取出对应节点）和一个双向链表（用于维护 LRU），导致其实现在实际应用中较为臃肿。

Redis 并未实现严格的 LRU，通过对redis对象新增一个最近访问时间属性，采用**近似 LRU**算法

1. 从键空间中随机抽取一小部分键

   默认 5 个, 可通过 `maxmemory-samples` 配置

2. 每个键维护一个访问时间戳（基于 `LRU_CLOCK`）。

3. 比较采样键的访问时间，淘汰最旧的键。

   Redis 使用一个全局 LRU 时钟（精度为 1 秒），每次有读写请求进来时，将全局LRU时钟的值设置为该次读写请求的TTL，

   不用每次都去查询高精度的系统时钟



近似LRU算法意味着有可能出现选取多个键都是最近经常访问的键，导致删除掉一些热点键，因此需要权衡调优

这种近似 LRU 算法在性能和精度间取得平衡，采样越多，精度越高，但开销也越大。

下图表示, 在samples等于10的情况下redis LRU算法的品质就比较好了

![近似LRU的效果](https://raw.githubusercontent.com/HarveyBlocks/blog_assets/refs/heads/main/Redis%26Cache/原理/Day14-过期淘汰策略/近似LRU的效果.png)

LRU算法不能避免**缓存污染**问题: 如果同一时间有大批量只被访问一次的数据加入redis，那么就会导致一些热点key被识别为最久未被使用而被删除

缓存污染问题并不是普遍发生的问题，仅针对特定系统LRU方案并不适配，为了解决污染问题，redis4.0后引入LFU算法来解决这个问题

#### allkey-lru

> 全局最近最久未被访问

从所有键中选择最少使用的键进行删除。无论是否设置了过期时间都有可能被淘汰

如果有一些key是不可删除的，那就可能会造成一些错误，具有局限性

#### volatile-lfu

> Least Frequently Used 最近最不经常使用

仅对设置了过期时间的键使用 LFU 最不常用算法进行淘汰。

与 volatile-lru 类似，但更注重**访问频率**。



**lru**算法对象头24位全用于存储最近访问时间戳

**lfu**算法对象头前16位用于存储最近访问的时间戳，后八位保存 logc(访问频次)



每个新加入的key的logc是5，越小越容易被淘汰

logc不是单纯的访问次数，它会随着访问之间衰退，每次访问key，logc衰退

- 衰退的大小由这次访问和上次访问的时间差来决定，越久没访问，这个衰退就越大，就越容易被淘汰

之后会对logc计数器进行增加都有可能会增加（节省内存）

- logc越大增加的概率越低这种策略可以反映近期热点
- 使redis数据不会过分的受到历史热点的影响





#### allkeys-lfu

> 全局最近最不经常使用

对所有键使用最不经常使用算法



#### volatile-ttl

> 根据过期时间优先

从设置来过期时间的键中选择剩余时间最短的键进行删除





#### volatile-random

> 随机删除

在大部分的使用场景中，随机删除都不是一个最佳的方案，可能误删高价值数据。



#### allkey-random

> 全局随机删除

测试环境可能会使用。



### 淘汰模式

#### Fast 模式和 Slow 

Fast 模式和 Slow 模式并不是 Redis 的淘汰策略，而是 Redis 在执行内存淘汰时的**算法运行模式**，

决定了淘汰算法的执行效率和精度。

由 `maxmemory-eviction-tenacity` 参数控制（Redis 7.0 及以上版本引入）。

- **0**：始终使用 Fast 模式。
- **100**：始终使用 Slow 模式。
- **中间值**（如 10、50）：根据内存压力动态选择 Fast 或 Slow 模式，值越大越倾向于 Slow 模式。

**Fast 模式**：

- 快速执行，采样较少的数据（通常是少量随机样本）。
- 性能开销低，适合高并发场景。
- 精度较低，可能导致次优的淘汰选择。
- 需要快速响应的场景。

**Slow 模式**：

- 采样更多的数据，执行更精确的算法（如 LRU/LFU 的完整计算）。
- 淘汰选择更准确，能更好地保留高价值数据。
- 性能开销较高，可能影响响应速度。
- 对数据保留精度要求高的场景。



Fast 模式可能导致次优淘汰（误删高价值数据），但响应快。

Slow 模式淘汰更精准，但性能开销大。

### 监控与调优

- 查看命令
  -  `INFO MEMORY` 
  -  `MEMORY STATS` （redis4.0以上）
- 监控目标
  -  `evicted_keys` 由于内存淘汰策略被删除的键数累计
  -  `mem_used` redis 当前实际使用的内存字节数
- USAGE可以监控单个key的使用情况，在大key问题中也会用到

如果 `evicted_keys` 持续上升，说明内存紧张，且当前淘汰策略可能导致重要数据被频繁驱逐。

调整 `maxmemory-samples` 和 `maxmemory-eviction-tenacity` 优化淘汰效果。



### 碎片回收

默认通过jemalloc来管理内存(**jemalloc** 是一个高效的内存分配C库)

jemalloc 并不立即将释放的内存返回给操作系统，而是先在内部保留，重复利用以减少向系统申请/释放内存的开销，极端情况下可能导致内存的爆满

jemalloc 为每个线程或线程组分配独立的 arena(jemalloc 的 **内存池**)，减少多线程环境下的锁竞争

jemalloc很快，它在后台线程合并碎片块
